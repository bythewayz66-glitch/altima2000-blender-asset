# ALTIMA2000 — 2000 Nissan Altima (L30) fully disassemblable Blender asset

A procedurally generated, photorealistic 2000 Nissan Altima sedan in **gold metallic**,
split into **2,130 individually selectable, separately named parts** organised into a
16-category / 57-sub-collection tree, with **real routed wiring** (323 wire segments in
31 harnesses, 192.9 m of wire), **real routed hoses and tie straps** (37 hose segments +
38 tie straps, 23.7 m), a machine-readable assembly manifest **plus a per-module manifest
for each of the 7 module files**, a working disassemble / reassemble toolkit, a **27-step
full-car exploded sequence**, a **keyframed teardown animation exported to glTF**, and a
**touch-activated wire glow with a progressive trace** including a **live modal operator**
and a **per-harness visibility panel** (see §11 and §12).

Everything here is generated by Blender Python — there is no downloaded or third-party
mesh in the asset. Running the build script reproduces the whole car deterministically.

**Repository:** https://github.com/bythewayz66-glitch/altima2000-blender-asset (public, branch `main`).
**Release:** https://github.com/bythewayz66-glitch/altima2000-blender-asset/releases/tag/v1.0.0 — the
`.blend`, `.glb` and `.fbx` files are attached as downloadable release assets.
Large binaries are stored with Git LFS. See **HANDOFF.md** for the full handoff.

## 2. Naming convention

Every object name matches this regex, enforced at build time (`bad=0` on every build):

```
^ALTIMA2000_(BODY|SHEL|DOOR|GLAZ|MIRR|MLDG|SEAL|INTR|SEAT|ELEC|LAMP|ENG|TRN|EXH|SUSP|STR|BRAK|WHL|FAST|SCRE|CLIP|FLUD|EMIS|SAFE|BATT)_[A-Za-z0-9]+_[A-Za-z0-9]+(_[0-9]{3})?$
```

Human-readable form:

```
ALTIMA2000_<GROUP>_<Tag>_<Detail>[_<NNN>]
```

| Field | Meaning | Examples |
|---|---|---|
| `ALTIMA2000` | Fixed asset prefix. | |
| `<GROUP>` | 3–4 letter system code (table below). | `BODY`, `ENG`, `FAST` |
| `<Tag>` | The component family / assembly. | `Door`, `ValveCover`, `Bolt` |
| `<Detail>` | Variant within the family — usually the corner. | `FL`, `FR`, `RL`, `RR`, `Front`, `Rear_Left` |
| `_<NNN>` | Zero-padded sequence, **only** when a family has more than one instance. | `_001` … `_084` |

Corner codes are always from the driver's perspective: **F**ront/**R**ear + **L**eft/**R**ight,
so `_FL` is the front-left corner. `_L` / `_R` alone mean "left side / right side".

## 5. Disassemble / reassemble / explode

The `.blend` ships with three operators. Open the file, run
`altima2000_assembly_tools.py` once from the **Text Editor** (*Run Script*), then use the
**Altima 2000** tab in the 3D Viewport sidebar (press `N`) — or the operator search (`F3`).

| Operator | Blender id | What it does |
|---|---|---|
| Disassemble (Explode View) | `altima.disassemble` | Radially displaces every part away from the explode centre, storing each part's assembled position first. Params: **Distance** (0–5), **Centre**, **Selected Only**. |
| Reassemble (Assembly View) | `altima.reassemble` | Restores every part's location and rotation from its stored `asmb` transform. |
| Verify Assembly | `altima.verify_assembly` | Checks every part against its stored position within a tolerance and reports any that are misplaced. |

Typical loop: **Verify Assembly → Disassemble → Reassemble → Verify Assembly** (the last
check confirms the car returned to its exact build state).

### How the reassembly actually works

Every part carries a custom property `asmb` (visible in *Object Properties ▸ Custom
Properties*) holding its canonical transform:

```json
{
  "loc": [0.12, -0.781, 0.688],
  "rot": [0.0, 0.0, 0.0],
  "collection": "Body_Panels",
  "part": "Side_R",
  "group": "BD",
  "sub": "Side",
  "template": ""
}
```

`"template"` is non-empty when the part shares its mesh datablock with siblings (fasteners,
clips, hoses) — see §6. So reassembly is exact and **does not depend on the manifest file**;
the manifest is a second, external copy of the same data.

### Reassembling programmatically

```python
import bpy, json

manifest = json.load(open("altima2000_manifest.json"))

for row in manifest["parts"]:
    ob = bpy.data.objects.get(row["name"])
    if ob is None:
        continue
    ob.hide_viewport = ob.hide_render = False
    ob.location       = row["offset_m"]
    ob.rotation_euler = row["rotation_euler_rad"]
    ob.scale          = row["scale"]
```

Or straight from the `.blend`, with no manifest at all:

```python
import bpy
for ob in bpy.data.objects:
    info = ob.get("asmb")
    if info:
        ob.location       = info["loc"]
        ob.rotation_euler = info["rot"]
        ob.hide_viewport  = ob.hide_render = False
```

## 6. Why 2,075 parts but 1,281 meshes

A real car has thousands of identical fasteners. Modelling 2,075 unique meshes would be
wasteful, so bulk families (bolts, nuts, clips, hoses, tie straps, fuses) share one mesh
datablock per size/template while remaining **2,075 separate objects** — each still
individually selectable, individually named, individually transformable, and each with its
own manifest row. The manifest's `instance_of` column tells you which objects share a mesh;
`instance_families` gives the counts per template.

Result: 81,616 vertices / 79,657 faces for the entire car.

## 10. Known limitations

- **Body panels are surface shells**, not solid stampings: each panel is a correctly
  shaped, correctly placed skin with real thickness via a Solidify pass, not a modelled
  inner pressing with ribs and flanges. Panel gaps are geometric, not stamped flanges.
- **Fastener and clip positions** are distributed deterministically across each
  assembly's bounding volume rather than derived from real torque-spec locations.
  They are correctly named, grouped, counted and transformable, but a purist concours
  teardown would want them individually placed.
- **Engine internals** (crank, cams, pistons) are representative volumes at correct
  positions and orientations, not dimensioned to factory drawings.
- **Interior** is modelled to the visible surfaces plus seat structures; underside
  bracketry is simplified.
- Renders are Cycles CPU at 28 samples — clean enough for verification, not for
  marketing.
- **Wire routing is plausible, not factory-exact.** Each harness follows the real
  component-to-component path (fuse box → firewall grommet → ECM, body → A-pillar
  grommet → door, etc.) with Catmull-Rom bends, but the waypoints are derived from the
  asset's own component positions rather than a Nissan service manual. Wire gauges are
  representative per circuit type (power / signal / ground), not per factory spec.
- **The glow / trace is a viewport-and-render shader effect**, not a game-engine
  interaction. It is driven by a baked mesh attribute plus material node values, so it
  survives disassemble / reassemble / explode and is regenerated by every build, but a
  runtime engine would need to re-implement the same attribute-driven emission.

## 12. Real wiring (v3)

Every wire in the car is **real geometry** — a swept tube with its own mesh, its own
object, its own name and its own manifest row. Nothing is a texture, a painted line or a
decal. Wires can be selected, hidden, moved and removed exactly like any other part.

| Metric | Value |
|---|---:|
| Wire segments (individually selectable objects) | **323** |
| Harnesses | **31** |
| Total wire length | **192.9 m** |
| Bulkhead grommets | 15 |
| Loom retainer clips | 168 |
| Connector shells | 62 |
| Wire materials (insulation colours) | 10 |

### How a harness is built

A harness is a bundle of **circuits** (differently-coloured insulated wires) that share a
route. Each circuit is split into **segments** at the route's waypoints, so a segment is a
removable piece of the run exactly like a real harness section. Along every route the
build also places the hardware a real loom has: **grommets** where the run passes through a
bulkhead or panel, **P-clips / retainers** that hold the loom to the body, and
**connector shells** at each end.

Routing is smoothed with a Catmull-Rom spline through the waypoints and resampled to
uniform spacing, so runs bend around structure instead of running as straight
point-to-point lines. The circuits in a bundle are fanned out slightly so the loom reads
as a bundle rather than a single fat wire.

```
ALTIMA2000_ELEC_Wire_<Harness>_<NNN>       wire segment
ALTIMA2000_ELEC_Grommet_<Harness>_<NNN>    bulkhead grommet
ALTIMA2000_ELEC_WireClip_<Harness>_<NNN>   loom retainer clip
ALTIMA2000_ELEC_WireConn_<Harness>_<NNN>   connector shell
```

They live in six new `Electrical_*` sub-collections (Engine, Dash, Cabin, Body, Door,
Chassis) alongside the existing `Electrical_Harness` / `_Battery` / `_Modules` /
`_Lighting`. Because they are ordinary parts, they appear in the manifest, in the
disassemble / reassemble round trip, and in the exploded view with no special handling.

### Manifest

The manifest carries a `wiring` block:

```json
"wiring": {
  "wire_segment_count": 323,
  "harness_count": 31,
  "total_wire_length_m": 192.92,

    "mesh_attribute": "trace_t",
    "domain": "POINT",
    "meaning": "normalised arc length along the run (0.0 start, 1.0 end)",

  },
  "systems": { "EngineMain": { "circuits": [...], "wire_segments": 20, ... }, ... },

               "harness": "EngineMain", "circuit": "Power",
```

`trace_points` is the flattened poly-line of the run, so a downstream tool can rebuild

## 13. Touch-activated glow and progressive trace

Select a wire and run **Trace Wire (Touch Glow)** — the wire lights up, and the glow
**travels along its run from one end to the other** rather than switching on as a whole.

### How it works

Every wire mesh carries a baked float attribute `trace_t` on the **POINT** domain: the
normalised arc length along the run, `0.0` at the start and `1.0` at the end. The wire
materials read that attribute through a small node chain:

```
trace_t ──▶ Map Range (From Min = TraceProgress − TraceWidth,
                       From Max = TraceProgress)  ──▶ × GlowStrength ──▶ Emission Strength
```

Three named Value nodes drive it, and they are what the operator animates:

| Node | Meaning |
|---|---|
| `TraceProgress` | How far along the run the glow has reached (0 → 1) |
| `TraceWidth` | Soft leading-edge width of the glow band |
| `GlowStrength` | Peak emission strength |

Sweeping `TraceProgress` from 0 to 1 makes the lit band travel from the start of the wire
to its end. Because the mask is computed **per vertex** from the baked attribute, the
leading edge is a real gradient along the wire — not a whole-object on/off switch.

### Operators

| Operator | Blender id | What it does |
|---|---|---|
| Trace Wire (Touch Glow) | `altima.trace_wire` | Lights the selected wire(s) progressively end to end. Params: **Glow Strength**, **Trace Width**, **Steps**, **Delay**. |
| Trace All Wires | `altima.trace_all` | Runs the trace over every wire in the scene, in name order. |
| Clear Wire Glow | `altima.trace_clear` | Switches every wire glow off. |

All three sit in the **Altima 2000** sidebar tab (`N` in the 3D Viewport), under
*Wire Glow / Trace*.

### Programmatic use

```python
import bpy
ns = {"bpy": bpy, "__name__": "altima_trace"}
exec(open("altima2000_assembly_tools.py").read(), ns)

ns["trace_set"](0.5, 6.0, 0.12)          # every wire lit halfway along
ns["trace_wire_impl"](bpy.data.objects["ALTIMA2000_ELEC_Wire_EngineMain_001"],
                      strength=6.0, width=0.12, steps=24)
ns["trace_clear"]()                       # all off
```

### Compatibility

The effect is driven by a **mesh attribute** plus **material node values** — not by a
modifier, a driver or a per-object hack. It therefore survives the disassemble /
reassemble / explode operators, is preserved in the `.blend` and the glTF export, and is
regenerated by every build. `renders/glow_*` shows the wires lit.
